Chapter 01 JWT middleware skeleton ▶ 00:00

We started with a single identity resolution layer so handlers never have to care which auth path was used — Bearer token for the CLI, or the ls_session cookie for the browser.

The Authn middleware extracts whichever is present, verifies it, and injects the resolved Identity into the request context. Downstream handlers call one auth.From(ctx) helper.

Goapi/internal/auth/authn.goClip · 01:12
// Authn resolves a principal from Bearer token or ls_session cookie.
func Authn(next http.Handler) http.Handler {
  return http.HandlerFunc(func(w, r) {
    token, err := extractToken(r)
    if err != nil { http.Error(w, "unauthorized", 401); return }
    claims, _ := ws.Verify(token)
    next.ServeHTTP(w, r.WithContext(ctxWith(claims)))
  })
}
Chapter 02 Database migration 002 ▶ 12:40

users stores the Google-sourced identity with a unique constraint on google_sub. auth_sessions stores CLI refresh tokens as a hash with expiry and a soft-revoke flag — a compromised device grant can be killed without rotating the signing secret.

Viewer Inject@sec_r0 · 13:55
"Why store the token hash rather than the full token?"
JWTs are stateless, so expiry alone can't revoke a compromised token early. Storing the hash gives us a revoke-able allowlist — one extra DB lookup per refresh, worth it for security.
Chapter 03 CLI device flow ▶ 38:55

The CLI calls POST /auth/device/start, which creates a pending grant in Redis and returns a device_code plus a browser URL. The CLI polls until approved, then writes the token pair to ~/.liveshortly/credentials.json — auto-refreshing from then on.
