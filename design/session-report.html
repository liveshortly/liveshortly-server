Chapter 1 · 00:00 +00m 00s into session
Let's build the auth middleware. Go API needs JWT on every route — Bearer for CLI, cookie for web.

We'll start by designing the identity resolution layer — a single middleware that can handle both authentication paths without forcing handlers to care which one was used.

The Authn middleware will extract a token from either the Authorization: Bearer <jwt> header (CLI path) or the ls_session HttpOnly cookie (web path), verify it, and inject the resolved Identity into the request context. Downstream handlers call a single auth.From(ctx) helper — they never touch tokens directly.

1// Authn resolves a principal from Bearer token or ls_session cookie. 2// Returns 401 if neither is present or valid. 3func Authn(next http.Handler) http.Handler { 4 return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { 5 token, err := extractToken(r) 6 if err != nil || token == "" { 7 http.Error(w, "unauthorized", http.StatusUnauthorized) 8 return 9 } 10 claims, err := ws.Verify(token) 11 if errors.Is(err, ws.ErrExpired) { 12 http.Error(w, "token expired", http.StatusUnauthorized) 13 return 14 } 15 ctx := context.WithValue(r.Context(), identityKey, identityFrom(claims)) 16 next.ServeHTTP(w, r.WithContext(ctx)) 17 }) 18}
Key Design Decision
Both Bearer and cookie tokens share the same JWT format and verification logic — only the extraction path differs. This means the API doesn't need two separate auth stacks, and tokens issued by either flow can be verified by the same ws.Verify() call. The typ claim ("web" vs "access") distinguishes them post-verification if a handler needs to know.

Now let's do the database migration — I need users and auth_sessions tables before the OAuth callback can work.

The auth migration adds two tables. users stores the Google-sourced identity (sub, email, handle, avatar URL) with a unique constraint on google_sub for upsert-on-login. auth_sessions stores CLI refresh tokens as JWTs with expiry and a soft-revoke flag — this lets the device flow issue long-lived sessions that can be invalidated without needing the secret.

We add owner_id as a foreign key on the existing sessions table so we can filter by user — and an index on it since every dashboard query will filter by owner.

@devuser_99 Viewer +13m 55s
Why store the token hash rather than the full token? Couldn't you just check expiry in the JWT itself?
Claude responded (via CLI injection)
Good question — JWTs are stateless by design, so expiry is in the claim. But if a CLI token is compromised, we need a way to revoke it without invalidating all tokens or changing the secret. Storing the hash gives us a revoke-able allowlist: we check the DB on each refresh poll, and set revoked=true to kill a specific session. The tradeoff is one extra DB lookup per token refresh — worth it for security.

Chapter 3 · 25:10 +25m 10s into session
Wire up the Google OAuth callback — it needs to upsert the user and set the ls_session cookie.

The Google OAuth callback flow: Google redirects to /auth/google/callback with a code param. We exchange it for an ID token, verify the token with Google's public keys, extract the user's sub (stable Google user ID), and upsert the users row. Then we issue a short-lived web JWT (24h, typ=web) and set it as an HttpOnly, SameSite=Lax cookie named ls_session.

The state param carries a CSRF nonce stored in a temporary cookie — we verify it on callback to prevent CSRF attacks before doing anything with the code.

Chapter 4 · 38:55 +38m 55s into session
Last piece — the CLI device flow. The hooks need an access token without a browser. Poll-based: start → poll → done.

The device flow is a classic OAuth-style polling exchange without browser dependency. The CLI calls POST /auth/device/start which creates a pending device grant stored in Redis with a short TTL, returning a device_code and a URL for the user to open in a browser. The browser flow authenticates the user and marks the grant as approved. The CLI polls POST /auth/device/poll with the device_code — once approved, it gets back an access token + refresh token pair, which the hook writes to ~/.liveshortly/credentials.json.

@alice_codes Viewer +44m 18s
Does the CLI auto-refresh on expiry or does it need the user to run ls login again?
Claude responded
Auto-refresh — the hooks check token expiry before each API call. If the access token is within 60s of expiry, they call /auth/device/refresh with the refresh token. The refresh token itself lasts 30 days; the user only needs to ls login again if that expires or if they explicitly revoke it.
The Full Auth Architecture
Two token types, same JWT secret: web (24h, from cookie) and access (1h, Bearer). Both resolved by the same Authn middleware. Device grants are ephemeral Redis keys (5min TTL). Refresh tokens are in Postgres with soft-revoke. The CLI stores credentials in ~/.liveshortly/credentials.json and auto-refreshes. Web sessions expire after 24h and the user re-authenticates via Google.
