Go Auth JWT Race Condition
⠿ Chapter 01 The Problem ▶ 0:00

It started, as these things always do, with a bug report that seemed deceptively simple. Users were getting 401 Unauthorized errors after successfully logging in — but only sometimes, and only on the second request. The kind of bug that makes you distrust everything you know about HTTP.

I'd been staring at internal/auth/middleware.go for about 20 minutes before I decided to just start a session and let Claude look over my shoulder. The best debugging partner I know doesn't get tired, doesn't check Slack mid-thought, and has read every Go spec ever written.

⠿ Chapter 02 Diagnosis ▶ 12:30

The first thing Claude did was ask to see the middleware chain. Not the broken function — the whole chain. That reframing shifted everything. The issue wasn't in our Authn middleware; it was in how we were passing the Identity context value downstream.

⌥ Viewer Inject @lx_dev · 29:12
"Why not use a mutex instead of a channel here?"
Good catch from the chat. I was already holding a channel for the wrong reason — we didn't need a mutex or a channel. We needed to stop sharing mutable state between goroutines entirely. This comment sent us down the path that ultimately found the real fix.

⠿ Chapter 03 Token Validation ▶ 28:45

The real problem turned out to be in websession/jwt.go. We were reusing a jwt.Parser across goroutines without realizing the parser held internal state that wasn't safe for concurrent access. Classic Go gotcha.

Go internal/websession/jwt.go · before fix Clip · 28:45 
// BUG: shared parser — not safe for concurrent use
var sharedParser = jwt.NewParser(
    jwt.WithValidMethods([]string{"RS256"}),
)

func Verify(tokenStr string) (*Claims, error) {
    token, err := sharedParser.ParseWithClaims(
        tokenStr, &Claims{},
        keyFunc,
    )
    if err != nil {
        return nil, err
    }
    return token.Claims.(*Claims), nil
}
⠿ Chapter 04 Writing Tests First ▶ 51:20

Before touching the implementation, Claude pushed us to write the tests first. This was the right call. Not because we're TDD purists — because the bug was timing-sensitive and we needed a reliable way to reproduce it before fixing it. We ended up with a race-condition test using testing/race that would have caught this the first time around.

Go internal/websession/jwt.go · fixed Clip · 1:24:45 
// FIX: create a new parser per call — zero shared state
func Verify(tokenStr string) (*Claims, error) {
    parser := jwt.NewParser(
        jwt.WithValidMethods([]string{"RS256"}),
        jwt.WithIssuedAt(),
    )
    token, err := parser.ParseWithClaims(
        tokenStr, &Claims{},
        keyFunc,
    )
    if err != nil {
        return nil, fmt.Errorf("jwt verify: %w", err)
    }
    claims, ok := token.Claims.(*Claims)
    if !ok || !token.Valid {
        return nil, errInvalidToken
    }
    return claims, nil
}

Yes — and the viewer linking that blog post at exactly this moment saved me at least 20 minutes. The sync.Pool gotcha with non-zero-safe types is well-documented, but I hadn't made the connection. Sometimes chat is the best documentation.
This viewer comment changed the direction of the session.

Once we understood what was happening, the fix was four lines. The lesson, as always with concurrent Go: don't share parsers, validators, or anything that holds internal parse state across goroutines. Create them per-request. The allocation overhead is negligible; the correctness guarantee is not.
